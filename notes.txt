## Chunking — Complete Learning Log

### Problem 1: Wrong PDF Parsing Library
**Observed:** pypdf extracted text in wrong sequence. Paragraph titles were grouping at the bottom, image captions appearing at top. Reading order was broken.

**Root cause:** pypdf reads PDF objects in storage order, not visual reading order.

**Solution:** Switched to pdfplumber which extracts text with coordinates — x0, y0, x1, y1 — giving us exact position of every word on the page.

**Lesson:** Library choice directly affects data quality. Understanding what your library actually does matters before writing any logic on top of it.

### Problem 2: Fixed Size Chunking Breaks Meaning
**Observed:** chunk_size=500 with overlap=50 was cutting sentences mid-thought. A fact about SF6 pressure could be split across two chunks. Neither chunk carried the complete meaning.

**Root cause:** Fixed character counting has no awareness of sentence or paragraph boundaries.

**Solution:** Moved to layout-aware chunking using line spacing detected from pdfplumber coordinates.

**Lesson:** Chunk boundaries should follow meaning boundaries, not character counts.

### Problem 3: Paragraph Detection Using \n\n Failed
**Observed:** Extracted text had no double newlines anywhere. Single \n was used for everything — new lines within a paragraph, between paragraphs, after headings — all looked identical in raw text.

**Root cause:** pdfplumber extracts words with coordinates, not formatted text. Whitespace structure of the original PDF is lost.

**Solution:** Used vertical gap between consecutive lines (gap_above, gap_below) as paragraph signal instead of newline characters.

**Discovered thresholds from real data:**
```
Normal line spacing:     ~16px  → same paragraph, continue
Gap > 20px (one side)   → new paragraph boundary
Gap > 30px (both sides) → section heading
```

**Lesson:** Never assume text formatting survives extraction. Go back to raw data and find the real signal.

---

### Problem 4: Section Detection Was Inaccurate
**Observed:** First line of paragraphs were being incorrectly tagged as section headers. Sections were misidentified throughout.

**Root cause:** Initial detection logic only checked gap on one side. A paragraph starting after a large gap looks identical to a section heading if you only check gap_above.

**Your insight:** Main header has large gap on bottom side only (no content above it). Sections have large gap on top AND the line above has larger font than body text.

**Solution:** Two-condition detection:
```
Main header: first line in document where gap_below > 30
Section: gap_above > 30 AND previous line font > body font size
```

**Lesson:** When a rule produces wrong results, look at the data around known correct examples. The diagnostic function showing 3 lines of context around a known heading revealed the exact signal needed.

---

### Problem 5: Text Skipping in Split Sections
**Observed:** Large sections split into part 1 and part 2 did not connect smoothly. Text from the original PDF was missing between parts.

**Root cause:** Character position drift. The old split logic used `rfind('.')` to find a nearby sentence boundary, which shifted the `end` position of each part. The next part started from a drifted position. Over multiple splits the drift compounded into gaps.

**Solution:** Sentence-first approach. Instead of tracking character positions:
```
Step 1: Split entire section text into sentences first
Step 2: Walk sentences one by one
Step 3: Fill current part until max_size reached
Step 4: Save part, start next part with next sentence
```

No character position tracking. No drift possible.

**Lesson:** When splitting text, always work at semantic boundaries — sentences or paragraphs — never arbitrary character positions. Position tracking accumulates errors.

Personal insight - Cosine vs L2:

Cosine measures angle only, ignores vector magnitude.
L2 measures actual distance in vector space.

Real example from my own experiment:
Question: "What precaution to be taken working with switchgear?"

Cosine result 3: Introduction chunk — talks about switchgear 
protecting the grid. Vectors point same direction (both about 
switchgear safety context) but the meaning drifts.

L2 result 3: Safety part 2 — directly about precautions near 
installed switchgear. More semantically precise.

Why this happened:
The introduction chunk may have similar directional language 
(fault protection, safety of grid) which aligns the angle —
but L2 penalized it because the actual vector distance was 
larger than the safety chunk.

My hypothesis for when each works better:
- Cosine → better when document length varies greatly
  (short chunks vs long chunks in same collection)
- L2 → better when chunks are similar length and 
  you need precise semantic proximity

The real answer: neither is always better.
It depends on your data distribution.
This needs experimentation per use case.

Next step: test with more questions to see if L2 
consistently outperforms cosine for safety/procedural 
questions in engineering documents.

Cosine vs L2 - Final Findings From My Data:

L2 wins for: Procedural and fault-condition questions
"What happens during fault?" → L2 gave better chunk order
Reason: Physical proximity in vector space better captures 
step-by-step procedural similarity.

Cosine wins for: Conceptual and alternative-seeking questions  
"Is SF6 harmful, any alternative?" → Cosine found the 
alternatives chunk correctly. L2 found SF6 alarm chunk —
related domain but wrong intent.
Reason: Cosine captures directional intent better. 
"SF6 harmful + alternative" has a specific semantic 
direction that cosine preserved.

Neither wins universally. It depends on question type.

Production decision for APEX2:
Start with cosine at threshold 0.6.
This is the safer default for a general Q&A system where 
users ask conceptual questions more than procedural ones.
Revisit if users report poor results on procedural queries.

Deeper insight:
The right long-term solution is Hybrid Search —
run both metrics, merge results intelligently.
This is called Reciprocal Rank Fusion (RRF).
Flag for Week 2 implementation.

Day 7 — Streamlit UI

New concept: Session State
Streamlit reruns entire script on every interaction.
Session state persists data between reruns.
Without it: client resets every question = slow.
With it: client built once, reused every question.

What "No data leaves your laptop" means:
- PDF processed locally by pdfplumber
- Embeddings computed by Ollama locally
- Vectors stored in local qdrant_storage folder
- LLM runs locally via Ollama
- No API calls to OpenAI, no cloud, no internet needed

This is the core product promise of APEX2.
